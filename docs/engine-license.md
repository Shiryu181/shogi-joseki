# 将棋エンジンのライセンスと、有料アプリでの使用

調査日: 2026-11-08。公開情報の整理であり、法律の助言ではない。確かめられなかったことは「未確認」と書く。

## 結論(先頭)

1. **使い方1(開発用にだけ使い、結果の JSON だけをアプリに同梱)は、GPL の面では問題が小さい。** GPL ソフトの「出力」には、原則として GPL の義務はかからない(FSF FAQ)。エンジン本体を iPhone アプリに入れなければ、アプリ側に GPL は及ばない、と読める。
2. **ただし水匠(SuishoPetite)の使用条件は、作者の文言を見つけられなかった(未確認)。** 評価値の数字を製品に使う分には GPL の話で足りる可能性が高いが、作者本人の条件は確認できていない。最も大きい穴はここ。
3. **使い方2(Web 版)は、リポジトリが公開で GPL-3.0-or-later のため、おおむね満たせている。** ただし「ソース提供」の形は不完全な点がある(下記「やること」)。
4. **アプリ(app/)にエンジンを入れない限り、App Store の有料配布は GPL とぶつからない。** 将来エンジンを入れるなら、App Store と GPL の相性が問題になる(最も危ない部分)。
5. **リポジトリ直下の LICENSE を GPLv3 にしたままだと、同じリポジトリの app/ も GPL と読まれやすい。** 自分で書いたコードは別ライセンスにできるが、Web 版(エンジン同梱)のコードと混ぜない整理が要る。

## 3. GPL ソフトの「出力」を有料製品に使えるか

- FSF FAQ(GPLOutput): 出力に GPL をかけることは「一般には法的に不可能。著作権法は出力の使い方に口出しを与えない」。例外は、プログラム自身の文章や絵の相当部分が出力にコピーされる場合。
- 同 FAQ(CanIUseGPLToolsForNF): エディタやコンパイラのような GPL の道具で書いた自作コードの権利は、道具の著作権の対象外。
- したがって、評価値の数字や「この手が良い」という判断は、エンジンの文章・コードの複製ではなく、GPL の義務の対象にならないと読める。解説文・JSON を自分の著作物として有料で配るのは GPL 上は問題になりにくい。
- 出典: https://www.gnu.org/licenses/gpl-faq.en.html (#GPLOutput, #WhatCaseIsOutputGPL, #CanIUseGPLToolsForNF)

## 4. 使い方1でアプリに GPL の義務はかかるか

- GPL の義務(ソース提供など)は、プログラムを「配布(conveying)」するときに生じる。単に自分で動かすだけなら条件なし(FAQ #NoDistributionRequirements:「Nothing. The GPL does not place any conditions on this activity.」)。
- 使い方1はエンジンを自分の手元で動かすだけで、アプリにはエンジンのコードも評価ファイルも入れない。出力(JSON)だけを配る。上の3のとおり出力に GPL はかからないので、**アプリ側に GPL の義務は生じない**と読める。
- 気をつける点: エンジンや評価ファイルの中身(NNUE の重み、ソース)を JSON や画像に写して同梱しないこと。評価値と手の列だけにする。
- 注意: 水匠の個別条件(2)は別枠で未確認。

## 5. 使い方2(Web 版)の義務は果たせているか

- リポジトリは公開(`gh repo view`: PUBLIC、https://github.com/Shiryu181/shogi-joseki)。
- 実際にしていること(README・public/ の確認結果)
  - 本アプリ自体を GPL-3.0-or-later で公開、LICENSE 全文あり。`/LICENSE.txt` で配信。
  - エンジンの GPL 全文を `/THIRD-PARTY-yaneuraou-LICENSE.md` で配信。
  - 「このアプリについて」画面でライセンス表記とソース入手先を表示(README に記載。画面そのものは今回見ていない)。
  - エンジンは未改変で、ソースは `mizar/YaneuraOu.wasm` と本家へのリンクで示している。
- 評価: Web 版は GPL 公開のため、ソースは公開リポジトリで入手できる。基本は満たせている。
- 不足の可能性(改善案)
  - ソースの提供は「同じバージョンの対応ソースが入手できること」が要点。第三者リポジトリへのリンクだけだと、そのリポジトリが消えると満たせなくなる。配布した版(7.6.3-alpha.0)のタグを自分のリポジトリにも固定しておくと安全。
  - 内蔵の評価ファイルのライセンスが GPL かは未確認(2参照)。
- 注: Web でブラウザにプログラムを配信するのは「配布」にあたる(サーバーで動かすだけなら配布でない。FAQ #UnreleasedMods)。Web 版は前者。

## 6. 直下の LICENSE が GPLv3 のとき、app/ を App Store で有料配布できるか

- 著作権者は自作コードを複数の非独占ライセンスで出せる(FSF FAQ:「release it under various different non-exclusive licenses at various times」)。したがって **自分だけが書いたコードなら、GPL で公開しつつ、別途 App Store 用に別ライセンスで配ることは理論上できる**。
- ただし次の制約がある。
  - すでに GPL で公開した版は取り消せない(FAQ:「this right cannot be withdrawn」)。公開済みの Web 版コードは GPL のまま残る。
  - 他人のコード(GPL のエンジン、第三者の部品)を含むものは、自分の一存で再ライセンスできない。app/ にエンジンを入れなければ、この問題は避けられる。
  - 外部から貢献(PR)を受けた場合は、その人の許諾も要る。
- 「リポジトリを同じにする」こと自体は問題ではないが、直下の LICENSE が GPLv3 だと、app/ もそのライセンスと読まれる。app/ に別ライセンスを明記するか、リポジトリを分けるのが安全。
- GPL と App Store の相性として知られていること
  - 2010〜2011年、GNU Go や VLC の iOS 版が App Store から外れた。FSF の法務担当は、App Store の利用制限(DRM など)が利用者の権利を制限するので GPL 違反になる、という立場。VLC の開発者も同様に主張した。反対意見もあった(VideoLAN の会長など)。
  - 要は **GPL のコードを App Store で配ると、Apple の規約が GPL の「追加の制限を課さない」条項と衝突する、という指摘**。
  - 自分が全コードの著作権者なら、自分のコードをその例外で配ることは可能。第三者の GPL コード(エンジン)を App Store 版に入れると、再ライセンスできないため、この衝突が生じる。
- 出典
  - https://www.gnu.org/licenses/gpl-faq.en.html
  - https://www.informationweek.com/it-leadership/apple-pulls-vlc-player-from-app-store
  - https://www.techspot.com/news/41908-apple-removes-vlc-app-from-app-store-gpl-to-blame.html
  - (FAQ の中に App Store の個別項目は取得範囲では見つからなかった。FSF 公式の App Store 見解は未確認。)

## 7. 将来、エンジンを使う場合

| 方法 | GPL | App Store | 水匠 | 評価 |
|---|---|---|---|---|
| アプリ内にエンジンを同梱 | アプリ全体が GPL の対象になりやすい。ソース提供が必要 | 6のとおり相性が悪い。審査や削除のリスク | 条件未確認 | 避ける |
| サーバーでエンジンを動かし、アプリは結果を受け取る | 動かすだけなら配布ではなく、ソース提供義務は生じにくい(FAQ #UnreleasedMods)。AGPL ではない | 問題なし(通信するだけ) | 条件未確認(サーバー上での商用利用は要確認) | 第一候補 |
| 別ライセンスのエンジン・評価関数 | エンジンが GPL なら同じ。評価関数だけ MIT の「つようら王11mini/micro」などがある | エンジン本体は結局 GPL の場合がある | 水匠を使わないので回避 | 評価関数だけの置き換えでは App Store 問題は解決しない |

- サーバー実行の場合のコスト(エンジンの計算量、費用、遅延)は別途設計が要る。
- どの方法でも、ユーザーの棋譜を送る場合のプライバシーポリシーが必要。
- アプリ内に入れる場合は、エンジン自体も MIT/BSD 系のものがあるかを調べ、専門家に確認する。今回は具体的な候補は調べていない(未確認)。
