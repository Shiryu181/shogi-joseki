## 結論(先頭)

1. **おすすめは「つようら王11mini」(MIT)。次点は「つようら王11micro」(MIT)。** 作者(やねうらお氏)本人の公式ブログが「MIT License で頒布」と書き、記事の動機が「商用利用可能な評価関数パラメーターが少ない」こと。商用条件が一番はっきりしている。水匠5より約R150〜200強いと作者が述べている(作者の自己申告)。
2. **ただし今すぐ替えられるとは限らない。** つようら王の「ファイル形式(NNUE の型)」と「必要なやねうら王のバージョン」が、公開記事のどこにも書かれていない(未確認)。作者の記事では、対応ビルドは FANBOX で配布され、Windows 64bit 版のみ。今使っている npm の WASM(K-P 型、v7.6.3-alpha.0、2021年版)で読めるかは、ダウンロードして中身を見るまで分からない。
3. **やることは3つ。** (a) FANBOX の配布物(無料公開)を取り、同梱の説明・LICENSE・型を確認する。(b) 公式の macOS 版(V9.00 の APPLEM1)に載るか試す。載らなければ、最新ソースから Mac 上でビルドする。(c) 載ったら、スクリプトのエンジン起動部だけ差し替えて測り直す。
4. **エンジン本体(やねうら王、GPLv3)はそのままでよい。** 開発用にMac上で動かし、出力(手と評価値)だけをアプリに同梱する使い方なら、エンジンの GPL は出力にかからない、と読める(docs/engine-license.md の3・4)。
5. **「評価関数が MIT」でも、エンジンは GPLv3 のまま。** エンジンをアプリに入れる場合は別問題(今回は入れない)。
6. **替えると、評価値の数字が変わる。** 章の基準(最善との差100以内、損230以上、唯一は次善との差100以上 など)は、測り直して当たり直す必要がある。全42章+咎め・変化が対象。

## 3. 動かす方法

### 3-1. 今のスクリプトの呼び方
- scripts/lib/engine-worker.cjs と scripts/verify-joseki.cjs が `@mizarjp/yaneuraou.k-p`(WASM)を `require` し、USI を `postMessage` で送っている。使う USI は usi / isready / setoption(MultiPV、USI_Hash、Threads) / position sfen / go movetime / stop / bestmove と、`info ... score cp ... multipv ... pv` の読み取り。
- エンジンの入れ替えで変わるのは「どう起動して、どう1行ずつ送受信するか」だけ。USI の中身は大きく変えなくてよい見込み。

### 3-2. ネイティブ版(Mac / Apple Silicon)に替える(おすすめ)
- 公式 GitHub リリース「やねうら王 V9.00 GitHub版」に macOS 用(Intel SSE4.2 / AVX2、M1 以降の3種)が同梱されている(アセット yaneuraou-V900-git-mac-all.7z。公式 wiki の説明では M1 以降は `APPLEM1` を選ぶ)。
  - https://github.com/yaneurao/YaneuraOu/releases/tag/V9.00
  - https://github.com/yaneurao/YaneuraOu/wiki (やねうら王のインストール手順)
- 評価関数は、実行ファイルのフォルダの `eval/` に `nn.bin` を置く。型は公式 wiki に一覧がある(標準 NNUE=halfkp_256x2_32_32、NNUE1024、halfkpe9、KP256、SFNN1536 など)。**エンジンのビルドが評価関数の型に対応している必要がある。**
- つようら王の型が公式 V9.00 のビルドに入っているかは未確認。入っていなければ、最新ソース(2026-11 も更新が続いている)を Mac 上でビルドする。ビルド手順は別 wiki「やねうら王のビルド手順」(今回は取得できず、未確認)。
- 呼び出しは Node の `child_process.spawn` で標準入出力に USI を流す形になる。ネイティブはWASMより速い(Apple Silicon でスレッド数も増やせる)。同じ時間でより深く読めるので、測定値は WASM より変わりうる。
- 現在の WASM は別プロセス(engine-worker.cjs)で落ちても作り直せる作りなので、同じ形をネイティブの spawn に置き換えられる。

### 3-3. WASM 版のまま替える
- 今のパッケージ(k-p)は評価ファイルを内蔵していて、型は K-P に固定。外部の nn.bin を差し込めるかは、README に書かれておらず未確認。つようら王が K-P でなければ、そもそも載らない。
- mizar 氏は halfKP 型など別のパッケージも出している(npm: @mizarjp/yaneuraou.halfkp。取得は 403 で、内容は未確認)。ただしその評価関数も内蔵で、つようら王は入らない見込み。
- 結論: WASM のまま替えるのは現実的でない。ネイティブが本命。

## 5. 替えたときの影響

### 強さ
- 作者の記載では、つようら王11mini は水匠5より約R150〜200強い。今の内蔵(SuishoPetite 2021-11)との比較は見つからず未確認。第三者による実測は見つからなかった。作者の自己申告として扱う。
- 同じ読み時間なら、強い評価関数のほうが正確。ただし「強い=評価値の目盛りが同じ」ではない。

### 基準の数字
- 評価値(cp)は評価関数ごとに目盛り(スケール)が違う。同じ局面でも、100差の意味が変わりうる。章の基準(最善との差100以内、損230以上、唯一は次善との差100以上 など)は、替えたあとの数字で当て直す必要がある(測り直して、判定が変わる手の一覧を作ってから基準を決める)。
- 基準自体を動かす前に、旧評価関数と新評価関数の判定の食い違いを一覧にして、ユーザーに見せる。
- 手の順位が変わる場合がある(特に「唯一の手」「許容」の境目)。解説文に書いた評価値・順位は、書き換え対象。

### 測り直しの対象と手間(見積もりは推測)
- 対象: 全42章の主手順の検証、各分岐の評価値、咎め手・変化(find-punishments、verify-deviations、analyze-critical、punish-depth など)。
- 手間の見積もり(推測)
  - エンジン差し替えと動作確認(ネイティブ版の準備、型の確認、1局面で旧新を比較): 半日〜1日。
  - 全章の再測定(スクリプト実行): ネイティブ版なら機械時間は数時間規模と思われる。実測が必要(今の WASM の所要時間は未計測)。
  - 結果の確認と解説・aims の直し(判定が変わった手の洗い出しと書き換え): 食い違いの量しだい。数日〜1週間規模の見込み。
- 先にやる小さな実験: 代表5〜10局面を旧・新で測り、評価値の差と判定の食い違いの割合を見る。割合が小さければ全面やり直しは軽く済む。

- 次点の考え方
  1. つようら王11micro(同じ記事・同じ条件。型も同じ見込み)。
  2. リゼロ評価関数(やねうら王公式。README に「一切の権利は主張しません」)。弱いが条件は明確。強さが足りるかは、代表局面で測って決める。
  3. 現状のまま(水匠 SuishoPetite の WASM)で、出力だけを使う。評価関数の条件は不明なまま。docs/engine-license.md の整理に従う。
- 今回は、第三者の評価関数(AobaNNUE 等)の個別の条件は調べていない(未調査)。
