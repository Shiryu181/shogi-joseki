# 評価関数の新旧比較(水匠 WASM と つようら王11mini ネイティブ)

2026-11-08。局面11個を、深さ16・18・20で測った。

## 結論
- **判定が食い違ったのは11個中4個**。基準(100以内・230以上・唯一)は、**そのままでは使えない**。
- 食い違いの向きは一方向ではない。新エンジンの方が厳しい(唯一でなくなる、100以内でなくなる)局面が2つ、緩い(咎めが230を超える、唯一になる)局面が2つ。
- 評価値の目盛りは新の方が大きい。大きな評価値の局面で新/旧 = 約1.4〜1.9倍(中央は約1.6倍)。つようら王の `FV_SCALE 24`(既定16の1.5倍)と合う。ただし「FV_SCALE のせい」とは確かめていない(推測)。
- 目盛りを一律に1.5倍しても揃わない。咎めの損は 0.85倍〜2倍と局面でばらつく(下の表)。基準を変えるなら、新エンジンで測った分布から取り直すのが安全。
- 前提: 旧は1スレッド(WASMはそれしかない)、新は7スレッド・ハッシュ1GB。スレッドを増やすと同じ深さでも結果が揺れる。1スレッド同士の比較ではない。

## 測り方
- 方法: 各局面で `go depth 20` を1回走らせ、その途中の深さ16・18・20の MultiPV(候補8手)を使う。
- 損: 候補の中にその手があれば最善との差。なければ、その手を指した後を探索して求める(verify-deviations と同じ)。
- 唯一: 最善手を指す場合の、次善との差。
- 判定の基準: 咎め=3つの深さすべてで損230以上。唯一=3つすべてで次善との差100以上。100以内=3つすべてで最善との差100以内。
- 局面は章のJSONから取った(`scripts/lab-out/engine-compare-cases.json`)。結果は同じフォルダの `engine-compare-wasm.json` と `engine-compare-native.json`。
- 選び方の偏り: 咎めの局面は、新エンジンでまず全咎め62個を深さ16で走査して損230〜650のものを拾い、PLAN.md に記録のあるものを優先した。新エンジン側に有利・不利が出ている可能性がある。
- 再現: `ENGINE=wasm|native node scripts/compare-engines.cjs cases.json out.json`

## 評価値の目盛り
同じ局面の最善手の評価値(手番側から見た値)を深さ16・18・20で比べた(新/旧)。
- F: 686/436, 733/451, 722/485 = 1.6, 1.6, 1.5倍
- G: 538/325, 527/276, 562/360 = 1.7, 1.9, 1.6倍
- H: 172/90, 164/100, 135/122 = 1.9, 1.6, 1.1倍
- J: 228/175, 183/157, 212/166 = 1.3, 1.2, 1.3倍
- 評価値が0に近い局面(I など)は比が大きく振れて参考にならない。
- 損の比(新/旧)も局面ごとに 0.85(D)〜約2(B)とばらつく。評価の形そのものが違うので、単純な倍率では換算できない。

## 時間(推測を含む)
| | 11局面の合計 | 1局面 |
|---|---|---|
| 旧(1スレッド) | 約6分 | 19〜56秒 |
| 新(7スレッド) | 約42分 | 14秒〜17分(中央値は約1分) |

- 新は局面によって極端に遅い。F・G の局面(大きく有利で、受けの手が多い形)は約15〜17分かかった(深さ20・候補8手)。
- 章JSONの局面は全部で3649(84章)。全局面を新エンジンの深さ20・候補8手で測ると、中央値1分でも60時間以上(推測)。実際は遅い局面に引っ張られてもっとかかりうる。
- 深さ16だけなら、走査の実績(7スレッド・候補4手で1局面約8〜12秒)から、3649局面で約10時間(推測)。
- verify-joseki のような「本線の局面を全部測る」作業と、咎めの検証(分岐のみ)で量が大きく違う。全部を測り直すのではなく、まず分岐・唯一と書いた手・100に近い手に絞るのが現実的。

## 不明な点
- 1スレッドで新を測った場合の差(時間がかかりすぎるため測っていない)。
- 局面を増やした場合に食い違い率が変わるか(11個での4個。母数が小さい)。
- 深さ18で E の損が測れなかった理由(子局面の探索が深さ18の出力を返さなかった)。
